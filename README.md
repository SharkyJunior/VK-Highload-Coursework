# VK-Highload-Coursework

## 1. Тема и целевая аудитория

> **Тема**: Google Photos

**Аудитория сервиса:**

- По данным Google на май 2025 года, сервис Google Photos достиг _1.5 млрд активных пользователей в месяц_ [^1]. Кроме того, общее количество загружаемых фотографий достигло 6 млрд/день. [^2]

**Функционал MVP:**

Аналог Google Photos будет иметь следующие функции:

- Авторизация
- Загрузка и скачивание фото
- Распознавание лиц на фото
- Поиск по галерее (дата, метаданные о камере, геоданные, лица в кадре)
- Возможность поделиться фото и видео
- Совместные альбомы (например, семейные)
- Уведомления при добавлении фото в совместный альбом

### 2.3 Технические метрики:

Для проектируемого сервиса принимаются два уровня подписки:

- бесплатный — **10 GB**;
- платный — **200 GB**.

Исследование All About Cookies показывает, что 62% опрошенных пользователей платят за облачное хранилище. [^7]

Оценочная доля Google в размере **15–19% рынка personal cloud**. [^8]

Для расчёта принимается 62% \* 17% = **10,5% платных пользователей**. Это рассматривается как отдельное инженерное допущение.

Количество пользователей тарифов:

```text
Платные:
1,5 млрд * 10,5% = 157,5 млн пользователей

Бесплатные:
1,5 млрд * 89,5% = 1,3425 млрд пользователей
```

Номинальный логический объём предоставленного пользователям хранилища:

```text
157,5 млн * 200 GB + 1,3425 млрд * 10 GB

= 31,5 млрд GB + 13,425 млрд GB
≈ 44,925 млрд GB
≈ 44,93 EB
```

Полученное значение **44,93 EB** является логической ёмкостью, то есть объёмом, доступным пользователям по тарифам. Для оценки реального физического объёма хранения необходимо учитывать репликацию данных.

Тогда необходимый физический объём для пользовательских данных:

```text
44,93 EB * 3
≈ 134,78 EB
```

Таким образом:

- **логическая ёмкость:** `≈44,93 EB`;
- **физическая ёмкость с учётом 3-кратной репликации:** `≈134,78 EB`.

Полученное значение не включает дополнительные накладные расходы самой storage-системы, такие как служебные метаданные, свободный резерв для восстановления после отказов, временное пространство, версии объектов, thumbnails и индексы, т.к. размеры этих категорий являются погрешностью на фоне размера хранилища для основного контента. Поэтому **134,78 EB следует рассматривать как минимальную оценку физического объёма данных с учётом только трёхкратной репликации**.

Дополнительно можно оценить объём фотографий через средний размер пользовательской галереи:

```text
1,5 млрд пользователей * 2795 фото
≈ 4,1925 трлн фото
```

При среднем размере одного фото около 5 MB:

```text
4,1925 трлн * 5 MB
≈ 20,96 EB
```

С учётом трёхкратной репликации:

```text
20,96 EB * 3
≈ 62,89 EB
```

Эта оценка ниже расчётной ёмкости тарифов `134,78 EB`, поскольку пользователи в среднем не обязаны полностью заполнять выделенные квоты. Поэтому в качестве расчётного верхнего уровня инфраструктуры используется значение, полученное из тарифов.

#### 2.3.1. Пиковый трафик (2х от нормального)

Т.к. у сервиса облачного хранилища практически не бывает пиковых сезонов, кроме праздников, когда множество людей будет делать больше фотографий, будем считать, что пиковый трафик будет превышать средний **в 2 раза**.

В реальности трафик будет более-менее равномерный в виду регионального распределения пользователей, но для большей надежности системы я заложил 2-кратный пик как самый худший и маловероятный, но тем не менее возможный сценарий (например, при изменении условий по подписке, например, больше места в том же тарифе, и большое количество людей за раз оформит подписку и начнет загружать фото).

## 3. Глобальная балансировка

Для сервиса масштаба Google Photos одного локального балансировщика недостаточно: пользователи распределены по всему миру, а основная нагрузка формируется большими объёмами загрузки и скачивания данных.

### 3.1. Функциональное разбиение по доменам

Внешние точки входа сервиса разделяются по назначению:

| Контур  | Домен                  | Основные операции                                                       | Глобальная политика   |
| ------- | ---------------------- | ----------------------------------------------------------------------- | --------------------- |
| **CDN** | `media.photos.example` | Upload / Download                                                       | **Home-region based** |
| **API** | `api.photos.example`   | Авторизация, поиск, метаданные, шеринг, совместные альбомы, уведомления | **Latency-based**     |

Для CDN пользователь получает домашний регион (`home region`), который хранится как атрибут аккаунта. Все обычные upload/download-запросы сначала направляются в CDN-пул его home-региона. Это уменьшает количество межрегиональных обращений к данным и упрощает поддержку репликации.

Для API домашняя привязка не используется: запрос направляется в здоровый API-регион с минимальной измеренной задержкой до пользователя. Такой принцип соответствует latency-based DNS-маршрутизации, при которой выбирается регион с наименьшей сетевой задержкой до клиента.

### 3.2. Обоснование расположения ДЦ

Пиковый media-трафик из раздела 2 составляет:

```text
Upload                         ≈ 5 556 Гбит/с
Download + shared album view   ≈ 1 146 Гбит/с

Итого CDN-трафик               ≈ 6 702 Гбит/с
```

Если ограничить максимальную пиковую нагрузку одного CDN-ДЦ значением **250 Гбит/с** (т.е. 10 сетевых карт по **25 Гбит/с**), минимальное теоретическое количество площадок:

```text
ceil(6 702 / 250) = 27 CDN-ДЦ
```

Однако простого деления на 27 недостаточно: нагрузка между географическими регионами различается в несколько раз. Поэтому количество площадок дополнительно определяется региональной нагрузкой. В проекте используется **32 CDN-площадки**, что позволяет оставить запас относительно лимита 250 Гбит/с и не создавать одного доминирующего ДЦ.

| BGP Anycast-регион                    | Доля нагрузки | CDN-площадок | Средняя пиковая нагрузка на одну площадку |
| ------------------------------------- | ------------: | -----------: | ----------------------------------------: |
| Северная Америка                      |          6,1% |            2 |                           **~204 Гбит/с** |
| Европа + Центральная Азия             |         14,3% |            4 |                           **~240 Гбит/с** |

### 3.3. Распределение API-запросов по ДЦ

API-трафик значительно меньше media-трафика: в пиковом режиме он составляет около **1,61 Гбит/с**, поэтому для API число площадок определяется в первую очередь требованиями к задержке и отказоустойчивости, а не пропускной способностью.

В проекте создаётся по две API-площадки в каждом из семи логических регионов:

| BGP Anycast-регион                    | API-ДЦ                 |
| ------------------------------------- | ---------------------- |
| Северная Америка                      | Ashburn, Dallas        |
| Европа + Центральная Азия             | Frankfurt, Warsaw      |
| Латинская Америка                     | São Paulo, Mexico City |
| MENA                                  | Dubai, Cairo           |
| Африка к югу от Сахары                | Johannesburg, Lagos    |
| Восточная Азия + Тихоокеанский регион | Tokyo, Singapore       |
| Южная Азия                            | Mumbai, Delhi          |

Для `api.photos.example` используется следующий алгоритм:

```text
Пользователь
     │
     ▼
Authoritative DNS
     │
     ▼
Latency-based routing
     │
     ├── ближайший здоровый API-регион
     │
     ▼
BGP Anycast VIP региона
     │
     ▼
один из API-ДЦ региона
```

Latency-based маршрутизация выбирает регион с минимальной измеренной задержкой среди доступных и здоровых регионов. При недоступности ближайшего региона запрос направляется в следующий по задержке регион.

После выбора API-региона BGP Anycast используется для выбора одной из нескольких точек входа внутри региона. Один сервисный префикс может объявляться с нескольких площадок, а сеть выбирает маршрут на основе своей глобальной топологии. RFC 4786 отдельно отмечает, что Anycast подходит для распределения сервиса между несколькими географическими узлами, но не гарантирует равномерное распределение нагрузки между ними. [^9]

Поэтому API Anycast используется прежде всего для выбора ближайшей и доступной точки входа и для failover, а не для точного распределения RPS.

### 3.4. Схема Anycast-балансировки

В данной работе выделяются семь логических **BGP Anycast-регионов**:

- Северная Америка
- Европа + Центральная Азия
- Латинская Америка
- MENA
- Африка к югу от Сахары
- Восточная Азия + Тихоокеанский регион
- Южная Азия

Для каждого региона CDN- и API-площадки объединяются в собственный пул входа. Внутри такого региона один и тот же сервисный префикс может анонсироваться несколькими площадками через BGP. Отказавшая площадка снимает анонс, после чего трафик переходит на другой Anycast-узел региона.

![Карта размещения CDN и API-ДЦ и BGP Anycast-регионов](global_dc_map.png)

На карте **кружки обозначают CDN-площадки**, **квадраты — площадки, на которых одновременно размещены CDN и API**, а штрихованные области обозначают логические BGP Anycast-регионы.

### 3.5. Схемы балансировки API- и CDN-запросов

Для CDN применяется home-region based routing:

```mermaid
flowchart TD
    U[Пользователь] --> DNS[DNS]
    DNS --> HR[Home-region based routing]
    HR --> R[Home BGP Anycast region]
    R --> C[CDN Anycast VIP]
    C --> D[Один из CDN-ДЦ региона]
```

Критерий выбора для CDN — **home region пользователя**. Это сохраняет близость media-трафика к основному месту хранения и репликации данных.

Для API используется latency-based routing:

```mermaid
flowchart TD
    U[Пользователь] --> DNS[DNS]
    DNS --> L[Latency-based routing]
    L --> R[Ближайший здоровый API-регион]
    R --> A[API Anycast VIP]
    A --> D[Один из API-ДЦ региона]
```

На уровне API допускается переключение между регионами, поскольку запросы к метаданным и индексам обслуживаются из реплицируемой инфраструктуры. Это позволяет выбирать ближайший по задержке регион без привязки к home region пользователя.

### 3.6. Механизм регулировки трафика между ДЦ

Для обоих контуров контролируются health checks, error rate и задержка. При отказе площадки её Anycast-анонс снимается, поэтому новый трафик перестаёт поступать на неисправный узел. RFC 4786 описывает именно такой принцип эксплуатации Anycast-сервисов. [^9]

Различие между контурами состоит в выборе резервной площадки:

| Контур | Основной критерий                | Failover                                                                                              |
| ------ | -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| CDN    | Home region + доступность данных | Другая CDN-площадка того же региона; при крупном отказе — доступная реплика данных в соседнем регионе |
| API    | Минимальная задержка             | Следующий по latency здоровый API-регион                                                              |

Для CDN нельзя автоматически отправлять запрос в любой ближайший ДЦ: резервная площадка должна иметь доступ к соответствующей копии данных. Для API такая привязка слабее, поскольку метаданные и индексы предполагаются доступными в нескольких регионах.

Таким образом, итоговая глобальная схема разделяет задачи:

```text
                         Пользователь
                              │
                  ┌───────────┴───────────┐
                  │                       │
             CDN/media                   API
                  │                       │
          Home-region based          Latency-based
                  │                       │
          BGP Anycast region      BGP Anycast region
                  │                       │
           CDN-площадки (32)          API-ДЦ (14)
```

DNS выполняет выбор логического региона, BGP Anycast — выбор доступной точки входа внутри выбранного региона, а локальный L4/L7-балансировщик из раздела 4 распределяет трафик между серверами конкретного ДЦ.

## 4. Локальная балансировка

После глобального выбора точки входа трафик необходимо распределить между серверами внутри конкретного дата-центра. Поскольку в разделе 3 CDN и API вынесены в отдельные контуры, локальная балансировка также выполняется независимо для этих двух типов трафика.

Для обоих контуров используется двухуровневая схема: L3-маршрутизация с ECMP распределяет входящий поток между несколькими L4-балансировщиками, после чего L4 распределяет TCP-соединения между L7-балансировщиками Nginx. На L7 выполняется TLS termination и маршрутизация запроса к нужному сервису.

Разница между контурами определяется характером нагрузки:

- CDN обслуживает основной объём сетевого трафика: upload и download. Здесь главным ограничением является пропускная способность сетевых интерфейсов и балансировщиков.
- API обслуживает небольшой по объёму, но более чувствительный к задержке трафик: авторизацию, поиск, метаданные, шеринг, совместные альбомы и уведомления. Здесь важнее низкая задержка обработки запроса.

### 4.1. Локальная балансировка CDN

После выбора home-region пользователя глобальным уровнем запрос попадает в один из CDN-ДЦ этого региона. Внутри площадки используется следующая схема:

```mermaid
flowchart LR
    A[CDN-трафик] --> B[L3 Router]
    B --> C[L4 LB]
    C --> D[L7 Nginx]
    D --> E[CDN / Storage Gateway]
    E --> F[File Storage]
```

L3-маршрутизаторы используют ECMP и распределяют входящие соединения между несколькими L4-балансировщиками. Такой подход позволяет избежать единственной точки отказа и равномерно загрузить L4-узлы.

На L4-уровне TCP-соединения распределяются между Nginx. Поскольку CDN обрабатывает большие объёмы данных, основным ограничением является throughput, а не количество HTTP-запросов.

Nginx на L7 терминирует TLS и передаёт запросы в CDN/Storage Gateway. Upload-запрос приводит к записи объекта в файловое хранилище, а download-запрос — к чтению объекта из кеша или файлового хранилища. Бинарные данные не проходят через основную БД: БД содержит только метаданные и ссылку на объект.

Для CDN запросы не перераспределяются между произвольными ДЦ внутри локального слоя: глобальная home-region based политика из раздела 3 сохраняет привязку пользователя к своему региону. При отказе площадки переключение выполняется на уровне глобальной балансировки, после чего новый трафик поступает в другой доступный CDN-ДЦ того же региона или к доступной реплике данных.

### 4.2. Локальная балансировка API

Для API после latency-based выбора региона запрос попадает в один из API-ДЦ выбранного региона. Внутри ДЦ используется отдельный пул балансировщиков:

```mermaid
flowchart LR
    A[API-трафик] --> B[L3 Router]
    B --> C[L4 LB]
    C --> D[L7 Nginx]
    D --> E[Auth]
    D --> F[Metadata]
    D --> G[Search]
    D --> H[Sharing / Albums]
    D --> I[Notifications]
```

L4 выполняет распределение TCP-соединений между Nginx, а L7 анализирует HTTP-запрос и выбирает нужный backend.

Для большинства коротких API-запросов можно использовать `round-robin`. Для запросов с существенно различающимся временем выполнения предпочтителен `least_conn`. Поисковые запросы и операции с метаданными могут иметь отдельные upstream-пулы, что позволяет независимо масштабировать эти сервисы.

В отличие от CDN, API-ДЦ не привязаны к `home_region` пользователя. Глобальный слой уже выбрал регион с минимальной задержкой, поэтому локальный уровень должен прежде всего равномерно распределять запросы между доступными экземплярами сервисов.

### 4.3. Отказоустойчивость

Все уровни локальной балансировки должны иметь резерв. Отказ одного L4 или L7-узла не должен приводить к отказу всего дата-центра.

Для L4 используется схема **N×2**. Сначала определяется минимальное количество узлов, необходимое для обработки пикового трафика, затем количество удваивается. Например, если для площадки требуется 3 рабочих L4-узла, разворачивается 6.

Для L7 используется схема **N+2**. К расчётному количеству рабочих Nginx добавляются два резервных узла. Если требуется 10 рабочих экземпляров, фактически разворачивается 12.

При отказе отдельного L4-узла ECMP исключает неисправный маршрут, а оставшиеся узлы продолжают принимать трафик. При отказе Nginx L4-балансировщик перестаёт направлять на него новые соединения.

Полный отказ дата-центра обрабатывается уже глобальным уровнем из раздела 3: для CDN трафик переводится на другую площадку home-region либо на доступную реплику, а для API — на следующий здоровый регион с подходящей latency.

### 4.4. Расчёт количества балансировщиков CDN

Пиковый CDN-трафик из раздела 3 составляет около **6 702 Гбит/с**. Он распределён между **32 CDN-площадками**, при этом максимальная расчётная нагрузка одной площадки составляет около **240 Гбит/с**.

Для расчёта принимаются следующие инженерные ограничения:

- один L4-сервер способен безопасно обработать до **80 Гбит/с**;
- один L7-сервер Nginx способен обработать до **25 Гбит/с**;
- для L4 используется запас **N×2**;
- для L7 используется запас **N+2**.

Значения 80 и 25 Гбит/с являются инженерными допущениями проекта. Реальная производительность зависит от CPU, сетевых карт, TLS-нагрузки, размера пакетов и характера трафика.

Количество узлов для каждой CDN-площадки:

```text
N_L4 = ceil(Пиковый_трафик_ДЦ / 80 Гбит/с) × 2

N_L7 = ceil(Пиковый_трафик_ДЦ / 25 Гбит/с) + 2
```

Например, для самой нагруженной CDN-площадки в Европе:

```text
Пиковый трафик ≈ 240 Гбит/с

L4:
ceil(240 / 80) × 2
= 3 × 2
= 6 серверов

L7:
ceil(240 / 25) + 2
= 10 + 2
= 12 серверов
```

Расчёт по регионам:

| BGP Anycast-регион                    | CDN-ДЦ | Пиковый трафик одного CDN-ДЦ | L4 на один ДЦ | L7 на один ДЦ | Всего L4 | Всего L7 |
| ------------------------------------- | -----: | ---------------------------: | ------------: | ------------: | -------: | -------: |
| Северная Америка                      |      2 |                  ~204 Гбит/с |             6 |            11 |       12 |       22 |
| Европа + Центральная Азия             |      4 |                  ~240 Гбит/с |             6 |            12 |       24 |       48 |
| Латинская Америка                     |      3 |                  ~206 Гбит/с |             6 |            11 |       18 |       33 |
| MENA                                  |      3 |                  ~194 Гбит/с |             6 |            10 |       18 |       30 |
| Африка к югу от Сахары                |      3 |                  ~174 Гбит/с |             6 |             9 |       18 |       27 |
| Восточная Азия + Тихоокеанский регион |     11 |                  ~213 Гбит/с |             6 |            11 |       66 |      121 |
| Южная Азия                            |      6 |                  ~212 Гбит/с |             6 |            11 |       36 |       66 |
| **Итого**                             | **32** |             **≤ 240 Гбит/с** |             — |             — |  **192** |  **347** |

Таким образом, для CDN-контура требуется ориентировочно **192 L4-балансировщика и 347 L7-балансировщиков**. Наиболее большое количество узлов приходится на Восточную Азию и Тихоокеанский регион, поскольку там расположено 11 CDN-площадок.

### 4.5. Расчёт количества балансировщиков API

Пиковый внешний API-трафик из раздела 2 составляет около **1,61 Гбит/с**. В соответствии с архитектурой раздела 3 он распределяется между **14 API-ДЦ**.

Для размерного расчёта принимается равномерное распределение как базовый сценарий:

```text
1,61 Гбит/с / 14 ≈ 0,115 Гбит/с на API-ДЦ
```

Фактическое распределение не обязано быть равномерным, поскольку глобальный слой использует latency-based routing. Однако даже при существенном skew нагрузки один API-ДЦ остаётся далеко ниже пропускной способности одного L4/L7-узла, принятой в проекте.

Для каждой площадки:

```text
N_L4 = ceil(0,115 / 80) × 2
     = 1 × 2
     = 2 сервера

N_L7 = ceil(0,115 / 25) + 2
     = 1 + 2
     = 3 сервера
```

При 14 API-ДЦ получаем:

| Показатель         | На один API-ДЦ | Всего для 14 API-ДЦ |
| ------------------ | -------------: | ------------------: |
| Пиковый API-трафик |    ~115 Мбит/с |        ~1,61 Гбит/с |
| L4                 |              2 |              **28** |
| L7 Nginx           |              3 |              **42** |

Таким образом, API-контур требует ориентировочно **28 L4** и **42 L7** узлов.

### 4.6. Итоговая схема локальной балансировки

В результате локальная архитектура имеет два независимых пула:

```text
CDN:
L3 / ECMP → L4 → L7 Nginx → CDN / Storage Gateway → File Storage

API:
L3 / ECMP → L4 → L7 Nginx → Auth / Metadata / Search / Sharing / Notifications
```

Для CDN локальная балансировка рассчитана от пикового сетевого трафика каждой площадки. Для API она рассчитана от RPS и небольшого сетевого объёма, поэтому пропускная способность балансировщиков не является ограничивающим фактором.

Суммарно для обеих плоскостей получается ориентировочно:

```text
L4 = 192 + 28 = 220 серверов
L7 = 347 + 42 = 389 серверов
```

При этом эти значения относятся именно к балансировщикам. Backend-сервера API, Storage Gateway, CDN-кеши и файловое хранилище масштабируются отдельно.

### 4.7. Выбор алгоритмов балансировки

На L4-уровне используется распределение TCP-соединений между доступными L7-узлами. Основная цель этого слоя — эффективно распределить сетевой поток и обеспечить отказоустойчивость.

На L7-уровне алгоритм выбирается по характеру сервиса:

- `round-robin` — для коротких API-запросов с близким временем обработки;
- `least_conn` — для запросов с различной длительностью выполнения;
- отдельные upstream-пулы — для независимого масштабирования Auth, Metadata, Search, Sharing/Albums, Notifications и CDN/Storage Gateway.

Такое разделение сохраняет простую локальную схему и одновременно позволяет независимо масштабировать CDN и API. Глобальный уровень отвечает за выбор региона и площадки, а локальный — за распределение нагрузки между экземплярами сервисов внутри выбранного ДЦ.

## 5. Логическая схема БД

Логическая схема описывает сущности сервиса и связи между ними без привязки к конкретной СУБД, способу хранения или шардингу. Отдельно показаны основная метаинформация, файловые данные, поисковый индекс, результаты распознавания лиц, кеши и буферы фоновых операций.

Расчёты нагрузки используют значения из раздела 2: около **4,1925 трлн фотографий**, средний размер файла **5 MB**, около **6 млрд загрузок/сутки**, **1,1925 млрд скачиваний/сутки**, **55,575 млн поисковых запросов/сутки**, **65,925 млн операций шеринга/сутки** и около **158 525 QPS** среднего пользовательского и фонового потока. Пиковая нагрузка принимается в 2 раза выше средней. Файловый контент при этом не проходит через основную БД: БД хранит метаданные и ссылку на объект, а байты файла обслуживаются файловым хранилищем/CDN.

**Служебные поля.** Во всех долгоживущих сущностях есть `created_at`. Там, где строку можно изменить, добавлен `updated_at`. Там, где строку можно удалить или отозвать пользователем, добавлен `deleted_at` (логическое удаление: строка остаётся в «корзине» 30 суток и потом удаляется фоновой задачей). Для неизменяемых и производных данных (`media_objects`, `face_embeddings`) `updated_at` не нужен: они не редактируются, а пересоздаются. Для временных буферов достаточно `created_at` и срока жизни (`expires_at`, `next_retry_at`).

Для каждой записи дополнительно учитывается **24 B** условных накладных расходов на структуру записи, выравнивание и информацию о nullable-полях. Это упрощённая оценка, поскольку реальные расходы зависят от СУБД и её формата хранения.

В расчётах используются десятичные единицы: 1 GB = \(10^9\) B, 1 TB = \(10^{12}\) B, 1 PB = \(10^{15}\) B и 1 EB = \(10^{18}\) B.

Полученные значения отражают расчётный объём записей, включая принятые накладные расходы на запись. Вторичные индексы, журналы транзакций, физическая репликация, свободный резерв СУБД и служебные структуры конкретного движка не включены. Для кешей и буферов применяется аналогичная оценка размера записей, но фактический расход памяти или диска может быть выше.

### 5.2. Файловые данные

Основной бинарный контент хранится отдельно от метаданных. Для каждой фотографии в `media_objects` хранится ссылка `object_key`, размер, checksum и тип файла, тогда как сами байты находятся в файловом хранилище и обслуживаются CDN.

При **4,1925 трлн фотографий** и среднем размере **5 MB** получается:

```text
4,1925 трлн × 5 MB ≈ 20,96 EB логического файлового контента
```

При трёхкратной репликации это около:

```text
20,96 EB × 3 ≈ 62,89 EB
```

Это независимая проверка объёма фотографий из раздела 2. Для верхней оценки инфраструктуры в работе остаётся более консервативное значение **134,78 EB физической ёмкости**, полученное из пользовательских квот 10 GB / 200 GB.

Важно, что **20,96 EB не означает, что такой объём проходит через основную БД**. В БД находятся только метаданные объектов, а большие файлы идут через CDN и файловое хранилище.

### 5.3. Кеши и буферы

Кеши и буферы являются частью логической схемы, хотя физически могут быть реализованы отдельными системами хранения. Их задача — уменьшить количество обращений к основной БД и хранить временное состояние незавершённых операций.

`session_cache` содержит идентификатор сессии, пользователя и время истечения срока действия. При 1,5 млрд записей и расчётном размере 64 B логический объём составляет около **96 GB**. Фактический расход оперативной памяти зависит от реализации кеша и её служебных структур.

`metadata_cache` содержит идентификатор фотографии, блок метаданных и TTL. При допущении о кешировании 1% фотографий получается около 41,925 млрд записей. При размере 304 B на запись расчётный объём составляет около **12,75 TB**. Источником истины остаётся таблица `photos`: при промахе кеша или истечении TTL данные читаются из постоянного хранилища.

`upload_buffer` хранит состояние незавершённых загрузок и информацию об отдельных чанках. При 6 млрд загрузок в сутки и TTL 5 минут среднее число одновременно активных загрузок оценивается как:

```text
6 млрд / 86400 × 300 ≈ 20,83 млн загрузок
```

Для метаданных одной незавершённой загрузки принимается размер 84 B:

```text
20,83 млн × 84 B ≈ 1,75 GB
```

Это только метаданные. Если предположить, что для каждой активной загрузки временно хранится в среднем 5 MB данных, объём временного бинарного контента составит:

```text
20,83 млн × 5 MB ≈ 104 TB
```

При двукратном пике соответствующая оценка возрастает примерно до **208 TB временного бинарного контента** и **3,5 GB метаданных загрузок**. Бинарные чанки предполагается хранить в отдельном временном файловом или объектном хранилище, а не в строках основной БД.

`notification_buffer` используется для повторной доставки push-уведомлений. При 67,5 млн уведомлений в сутки и TTL 1 час среднее количество событий в буфере составляет:

```text
67,5 млн / 86400 × 3600 ≈ 2,8125 млн событий
```

При расчётном размере одной записи 76 B логический объём метаданных очереди составляет:

```text
2,8125 млн × 76 B ≈ 213,75 MB
```

Фактический объём очереди может быть выше из-за служебных структур брокера, индексов, повторных доставок и задержек обработки.

### 5.4. Требования к консистентности

Для разных сущностей требуется различный уровень консистентности.

Для `users`, `sessions`, прав доступа в `shares` и структуры совместных альбомов (`albums`, `album_members`, `album_items`) требуется **сильная консистентность**. Нельзя допустить ситуацию, когда пользователь уже удалён или лишён доступа, но старое состояние ещё позволяет изменять альбом или читать защищённый ресурс.

Для `photos` и `media_objects` важна атомарность операции фиксации: запись считается завершённой только тогда, когда метаданные указывают на существующий объект. Сам бинарный объект после загрузки предпочтительно считать неизменяемым; обновления создают новую версию/объект, а не изменяют уже опубликованные байты.

`search_index`, `face_profiles`, `face_embeddings` и результаты `face_jobs` могут быть **eventually consistent**. После загрузки новая фотография может появиться в поиске и результатах распознавания с небольшой задержкой. Это приемлемо, поскольку эти данные являются производными от `photos` и `media_objects`.

Для `notifications`, `notification_buffer` и `face_jobs` применяется модель **at-least-once**. Повторная доставка или повторная обработка возможны, поэтому операции должны быть идемпотентными, а события должны иметь уникальный `event_id`/`job_id`.

Для кешей применяется **eventual consistency + TTL**. Источником истины всегда остаётся основное хранилище.

### 5.5. Распределение нагрузки по ключам

Основным ключом для пользовательских данных является `user_id`. Он используется при авторизации, доступе к галерее, настройках и части операций шеринга. Для равномерного распределения данных желательно использовать достаточно большое пространство идентификаторов, например случайные или хешированные значения, а не последовательные номера как физический ключ распределения.

Для фотографий естественный идентификатор — `photo_id`, но большинство пользовательских запросов сначала ограничивается владельцем. Поэтому логический доступ к галерее должен строиться вокруг составного ключа **`(owner_id, created_at, photo_id)`**. Это позволяет эффективно выбирать фотографии одного пользователя за заданный интервал времени. При этом один пользователь с очень большой галереей способен генерировать существенно больше чтений, чем средний пользователь, поэтому такая сущность является потенциальным источником skew.

Для `search_index` ключ должен начинаться с `owner_id`. Это важно, потому что поисковые запросы вроде «фотографии за 2024 год» сами по себе обладают очень высокой популярностью. Привязка индекса к владельцу не позволяет одному глобальному терму превратиться в единственный горячий ключ.

Для совместных альбомов естественный ключ — `album_id`. Чтения `album_items` и `album_members` концентрируются вокруг конкретного альбома. Поэтому особенно популярный семейный альбом может стать hot-key. Логически это решается разбиением доступа по времени и идентификатору элемента, например `(album_id, added_at, photo_id)`, без изменения модели предметной области.

`notifications` естественным образом распределяются по `recipient_id`. Основная нагрузка — выборка последних уведомлений одного пользователя. Здесь также возможен skew для очень активных аккаунтов, поэтому ключ должен дополняться временем создания.

Очереди и буферы (`face_jobs`, `upload_buffer`, `notification_buffer`) должны использовать случайные или хешированные идентификаторы, чтобы записи распределялись равномерно. Для очередей одновременно нужен индекс/логический порядок по `status + created_at` или `next_retry_at`, поскольку workers выбирают не произвольный объект, а готовые к обработке задачи.

Таким образом, схема сочетает три типа нагрузки: равномерные операции по идентификаторам пользователей/объектов, сильно локализованные запросы по владельцу и альбому, а также фоновые потоковые операции по очередям. Наиболее вероятные источники неравномерности — **крупные пользовательские галереи, популярные совместные альбомы и частые записи/чтения индекса поиска**.

Производные структуры (`search_index`, `face_embeddings`) обновляются асинхронно, а кеши и буферы разгружают постоянное хранилище и изолируют фоновые операции от пользовательского пути.

## 6. Физическая схема БД

Физическая схема привязывает таблицы из раздела 5 к конкретным СУБД. Стек выбран из классов хранилищ лекции под характер нагрузки каждой таблицы:

- **PostgreSQL** (реляционные, OLTP) — данные с сильной консистентностью: пользователи, сессии, альбомы, ссылки и права доступа. Это четыре независимые базы: `auth`, `albums`, `shares`, `user_access`.
- **Cassandra** (NoSQL, OLTP) — огромные объёмы с высокой нагрузкой на запись: метаданные фото, поисковый индекс, лица, уведомления.
- **Redis** и **Aerospike** (in-memory и SSD optimized) — кеши сессий и метаданных.
- **Kafka** (стриминговые) — задачи распознавания лиц и события между сервисами; **RabbitMQ** (брокер сообщений) — доставка push с повторами.
- **Ceph** (объектное хранилище) — байты файлов и буфер загрузок; **etcd** (координационные) — выбор лидера Patroni и карта шардов.

Данные каждого региона живут в контуре его `home_region` (п. 3.1). Глобальным остаётся только кластер `auth` (`users`, `sessions`). Шардирование в PostgreSQL нужно по объёму, а не по QPS: нагрузка на шард не превышает единиц QPS.

#### 6.2.1. Почему Cassandra, а не MongoDB

Наш профиль для `photos`, `search_index`, `face_*`: append-only запись неизменяемых строк (≈0,56 млн записей/с в пике суммарно по четырём таблицам), доступ только по ключу, 1–5 тысяч узлов, несколько ДЦ.

| Критерий        | Cassandra                                                                                                               | MongoDB                                                                                                              | Что важно для нас                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Запись          | Masterless: любая реплика принимает запись; LSM — commit log + memtable, последовательный I/O, без чтения перед записью | Один primary на шард (replica set); WiredTiger — B-дерево, случайный I/O                                             | 139k write QPS на каждую из 4 таблиц                              |
| Масштабирование | Добавили узел — токены перераспределяются, драйвер сам знает, куда идти (token-aware)                                   | Нужны `mongos`, config servers и балансировщик чанков; шард — это целый replica set из 3 узлов                       | 1 085 – 4 497 узлов на таблицу                                    |
| Несколько ДЦ    | RF задаётся на ДЦ (3 + 2), `LOCAL_QUORUM` не выходит за пределы home-DC                                                 | В replica set один primary на весь набор: запись из другого ДЦ идёт через него                                       | Запись в home-DC, асинхронная копия в DR-DC                       |
| Отказ узла      | Выборов нет, драйвер уходит на другую реплику                                                                           | Выборы нового primary, на это время запись в шард недоступна                                                         | Нет простоя записи при отказах                                    |
| Диск            | Строки лежат отсортированными по PK, отдельного индекса под PK нет                                                      | Обязательный индекс по `_id` плюс индекс по ключу шардирования: на 4,19 трлн документов это десятки TB лишнего диска | Узкие строки (154 B), индексы заметно раздувают объём             |
| Запросы         | Только по ключу партиции; нет join и ad hoc запросов                                                                    | Богатый язык запросов, вторичные индексы, агрегации                                                                  | Все запросы идут по `owner_id` / `user_id`: богатый язык не нужен |

Цена выбора: приходится денормализовать (п. 6.5), держать 50% диска свободным под компакшены (поэтому узел — 6 TB данных на 12 TB NVMe) и удалять мягко (`deleted_at`), чтобы не плодить tombstones. MongoDB выиграла бы при гибких запросах, вложенных документах и объёмах в единицы TB; здесь этого нет. Для таблиц, где нужны транзакции и уникальность (`users`, альбомы), берём PostgreSQL.

#### 6.2.2. Почему PostgreSQL для альбомов и доступа, а не Cassandra

Объём (≈50 TB) Cassandra бы выдержала. Выбор определяют не размер и не QPS, а семантика данных.

| Критерий                | PostgreSQL                                                                                                                    | Cassandra                                                                                                                                     | Что важно для нас                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Нагрузка                | 7,8k QPS на всё, ≈120 QPS на шард из 64                                                                                       | Рассчитана на сотни тысяч QPS записи                                                                                                          | Запись в альбомы в 50 раз меньше, чем в `photos` (2,6k против 139k QPS): преимущество Cassandra не нужно |
| Транзакции              | ACID на шарде: `album_items` + `album_members` + outbox одной транзакцией                                                     | Нет транзакций между партициями; logged batch атомарен только по записи, без изоляции; LWT работает в одной партиции и дорог (4 раунда Paxos) | Событие в Kafka (через outbox) не должно ни потеряться, ни уйти без изменения                            |
| Несколько путей доступа | Вторичные индексы ведёт сама СУБД в той же транзакции: у `album_items` три (по альбому, по порядку добавления, по `photo_id`) | Каждый путь — отдельная таблица, синхронизировать надо самим; materialized views считаются экспериментальными                                 | Страница альбома, `photo.deleted`, «мои альбомы», отзыв ссылок по `resource_id`                          |
| Целостность             | `UNIQUE`, `NOT NULL`, `CHECK`: фото не может попасть в альбом дважды                                                          | Запись по PK — это upsert, дубль молча перезапишет строку; уникальность только через LWT                                                      | Права и состав альбома нельзя портить гонкой двух запросов                                               |
| Изменяемость            | Строки часто меняются и удаляются (роли, `expires_at`, отзыв ссылки, фото убрали из альбома): MVCC + vacuum                   | Каждое обновление и удаление — новая версия или tombstone, чтение собирает версии из нескольких SSTable                                       | Cassandra нужна для неизменяемых строк (`photos`), альбомы к ним не относятся                            |
| Цена                    | 192 узла для `albums` (64 шарда × 3)                                                                                          | ≈45 узлов (50 TB / 6 TB × RF 5), но без индексов: вторые и третьи таблицы под другие ключи ещё увеличат объём                                 | 192 узла — около 2% от ≈8,9k узлов Cassandra: платим узлами за корректность                              |

`user_access` по одному ключу (`user_id`) подошла бы и Cassandra, но ей нужны два пути: список по дате и точечная проверка «есть ли доступ к ресурсу». В PostgreSQL это два индекса одной таблицы, в Cassandra — две таблицы. При 0,44 TB заводить для этого второй стек не оправдано.

#### 6.2.3. Поиск по лицу

Все запросы по лицам ограничены одним пользователем: чужие фото не сравниваются никогда. Есть два разных запроса, и ни один из них не перебирает индекс всех фото.

| Запрос                                                        | Как выполняется                                                                                                                                                                                                  | Сколько читает                                                |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Показать фото человека (чтение)                               | `face_photos`: партиция `(owner_id, face_id, year)`, строки отсортированы по `created_at DESC`, страница — `LIMIT 50`; идём от свежего года к старому                                                            | Одна партиция, ≈50 строк по ≈110 B                            |
| Отнести новое лицо к человеку (запись, воркер из `face_jobs`) | Читаем `face_profiles` пользователя (одна партиция, ≈10 centroid по 2 KB), считаем близость нового embedding к каждому centroid; выше порога — `face_id` этого человека, иначе `face_id = 0` («не распределено») | ≈20 KB и ≈10 сравнений 512-мерных векторов, доли миллисекунды |

Фоновая пересборка (Spark, по одному пользователю): берёт партиции `face_id = 0`, группирует лица, создаёт новых людей, пересчитывает centroid, переносит строки из `face_id = 0` в `face_photos` нового человека и обновляет `face_embeddings.face_id`. Перебор есть только здесь и ограничен нераспределёнными лицами одного пользователя. Так же исправляются дубли людей, если два воркера одновременно создали человека для одного лица. Онлайн-путь centroid не меняет, поэтому гонок на запись centroid нет.

`face_photos` — это и есть отдельный поисковый индекс из стека лекции: таблица, построенная под запрос. SAI по `face_ids` в `search_index` остаётся только для комбинированных запросов («человек + камера» и подобных) внутри партиции владельца.

Цена: ещё одна копия связи «фото — человек» (≈0,46 PB, ≈385 узлов с RF 3+2); слияние двух людей — фоновая перезапись строк `face_photos` (до десятков тысяч), в интерфейсе допускаем задержку; на `photo.deleted` нужные `face_id` берём из `face_embeddings` по `photo_id`.

Допущения для расчёта: 8,99 PB / 4,19 трлн фото ≈ 2,1 KB — один 512-мерный float32-вектор на фото, то есть ≈1 лицо на фото; строка `face_photos` ≈110 B (идентификаторы 8 B, `object_key` ≈64 B, `deleted_at`); ≈10 людей на пользователя (1,5 млрд пользователей).

### 6.3. Шардирование и резервирование (потаблично)

**Зачем шардируем и почему три базы:** `social` разделена на три базы по сервисам. У каждой свой ключ доступа, объём и жизненный цикл, поэтому и число узлов у каждой своё. Распределённых транзакций между ними нет: связь идёт через события (outbox → Debezium → Kafka), а внешних ключей между базами нет.

- **`albums`** (альбомы, участники, фото в альбоме): ≈50,4 TB с индексами. Пик ≈7,8k QPS (5,2k чтений + 2,6k записей), то есть ≈120 QPS на шард из 64; такое выдержал бы и один primary. А вот данных много, тогда как один узел PostgreSQL комфортно держит ≈2 TB: на этом объёме индексы ещё помещаются в RAM, а vacuum и восстановление из бэкапа укладываются в разумное время. По объёму нужно минимум 26 шардов (50,4 TB / 2 TB). Берём 64: (а) шард 0,8 TB восстанавливается ≈30 мин, единая база на 50 TB — ≈31 час; (б) запас роста ×2,5 до лимита 2 TB; (в) 4096 бакетов делятся поровну, а регионы получают целое число шардов по своей доле (NA 4 … EAP 22) — данные остаются в `home_region`; (г) сбой или порча шарда касается 1/64 альбомов. Ключ `hash(album_id)` держит все три таблицы альбома в одном шарде: транзакция локальная, 2PC нет.
- **`shares`** (266 GB) и **`user_access`** (437 GB): помещаются на один узел с запасом, шардировать их незачем. Это 7 региональных кластеров, по одному на `home_region`. Самый большой регион EAP (22/64 ≈ 34%) — 91 GB и 150 GB, восстановление ≈6 мин. `shares` попадает в кластер по коду региона в `share_id`; `user_access` — по `home_region` получателя.
- **`users`** (282 GB, 5,7k read QPS в пике, записей почти нет) не шардируется: он целиком помещается на один узел, а глобальная уникальность `email` при шардировании потребовала бы межшардовой проверки.

В Cassandra шардирование встроено (партиционирование по partition key): число узлов определяется объёмом (≤ 6 TB данных на узел) и записью 139k QPS.

Допущения для расчёта: шард PostgreSQL до 2 TB с индексами, узел Cassandra до 6 TB данных (12 TB NVMe, остальное под компакшены). Размеры индексов PostgreSQL — по п. 6.4, SAI в Cassandra около 25% (допущение).

**Порядок колонок в `user_access`.** В составном индексе сначала идут колонки с условием равенства (`user_id`, `resource_type`), затем колонка сортировки (`created_at DESC`), затем `resource_id` как tie-breaker для keyset-пагинации. Раньше индекс был `(user_id, created_at DESC)` без `resource_type`: запрос «только альбомы, свежие сверху» читал бы и ссылки и отбрасывал их после чтения. Теперь он спускается к `(user_id, 'album')` и читает ровно страницу. Общий список двух типов собирается слиянием двух отсортированных выборок в приложении. PK сделан `(resource_type, resource_id, user_id)`: для точечной проверки доступа порядок колонок не важен (заданы все три), а такой порядок отдаёт всех получателей ресурса одним диапазоном. Это нужно событиям `album.renamed` (копия `title`), отзыву и удалению альбома: один `UPDATE` на кластер вместо точечных запросов по каждому участнику. Для списка «что доступно пользователю» PK не подходит: `user_id` стоит последним, поэтому для этого запроса нужен отдельный индекс выше.

#### 6.5.2. Зачем `user_access`, если есть `shares`

| Таблица         | Роль                                                      | Где хранится                                    | На какой вопрос отвечает                       |
| --------------- | --------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| `album_members` | Источник истины: участники альбома и их роли              | «albums», шард по `album_id`                    | Кто в альбоме                                  |
| `shares`        | Источник истины: выданные доступы и ссылки (`expires_at`) | «shares», кластер региона из `share_id`         | Открыть ссылку; отозвать все доступы к ресурсу |
| `user_access`   | Проекция обеих таблиц по получателю                       | «user_access», кластер `home_region` получателя | Что доступно этому пользователю                |

Вопрос «что мне расшарили» задаётся по получателю, а источники разложены по `album_id` и по регионам `share_id`. Без проекции он уходит во все 64 шарда `albums` и во все кластеры `shares`: (1 042 + 1 526) пиковых QPS × 64 ≈ 164k запросов в секунду к шардам, причём время ответа определяет самый медленный шард. С проекцией — ≈2,6k запросов и один кластер региона получателя. Цена: 2,1 млрд строк, ≈0,44 TB с индексами (252 + 185 GB), то есть меньше 1% объёма `albums`. Хранить `shares` по получателю вместо проекции не стали: тогда scatter переехал бы в «отозвать все доступы к ресурсу». Регион получателя консьюмер событий берёт из `users` (async-реплика в своём регионе).

# 7. Алгоритмы работы системы

## 7.1. Алгоритм асинхронной обработки загруженной фотографии

**Подсистема:** загрузка фотографий, объектное хранилище, обработка
событий индексирование и распознавание лиц.

**Задача:** принять фотографию и сохранить её, не заставляя пользователя
ждать завершения всех фоновых операций --- построения поискового индекса
и анализа лиц.

**Входные данные и ограничения:** - идентификатор пользователя; -
бинарные данные фотографии; - метаданные: время съёмки, модель камеры,
геоданные и другие доступные атрибуты; - контрольная сумма файла; -
размер файла и ограничения на допустимый формат.

**Результат:** фотография сохранена в объектном хранилище, её метаданные
записаны в Cassandra, а событие о загрузке передано на асинхронную
обработку. После выполнения фоновых задач фотография становится доступна
через поиск и поиск по лицам.

**Последовательность работы:**

1.  API проверяет авторизацию пользователя, формат файла, размер и
    наличие обязательных полей.
2.  Storage Gateway принимает файл и при необходимости разбивает его на
    части. Части временно сохраняются в Ceph.
3.  После получения всех частей система проверяет целостность файла по
    контрольной сумме.
4.  Файл фиксируется в объектном хранилище Ceph, а метаданные фотографии
    записываются в Cassandra.
5.  После успешной фиксации система публикует событие `photo.uploaded`,
    содержащее идентификатор фотографии и необходимые ссылки на
    метаданные.
6.  Kafka сохраняет событие и передаёт его потребителям в
    соответствующих consumer groups.
7.  Сервис индексирования обновляет `search_index`, а обработчик
    компьютерного зрения обнаруживает лица и формирует их эмбеддинги.
8.  После завершения фоновых задач фотография становится доступна для
    поиска по соответствующим атрибутам и лицам. До этого момента
    возможна временная задержка появления результатов.

**Используемые структуры данных:** временные части файла в Ceph, объект
фотографии в Ceph, запись метаданных в Cassandra, событие
`photo.uploaded` в Kafka, поисковая запись в `search_index`, данные о
лицах в `face_embeddings` и `face_photos`.

**Альтернативы и обоснование выбора:**

- **Синхронная обработка в запросе пользователя.** Упрощает
  отслеживание результата, но увеличивает задержку загрузки и
  связывает доступность API с производительностью ML-обработки и
  индексирования.
- **Периодический поиск новых записей в базе.** Не требует событийного
  контура, но создаёт дополнительную нагрузку на базу и увеличивает
  задержку обработки.
- **Асинхронная обработка через Kafka.** Позволяет сглаживать всплески
  нагрузки, независимо масштабировать потребителей и повторно
  обрабатывать события.

**Влияние на БД и нагрузку:** операции записи метаданных выполняются
отдельно от вычислительно дорогого распознавания лиц. Kafka буферизует
поток событий, поэтому временное отставание обработчиков не должно
блокировать приём новых загрузок. При этом запись в Cassandra и
публикация события в Kafka не образуют общей атомарной транзакции. Для
надёжности необходим механизм гарантированной публикации событий ---
например, журнал событий или другой согласованный механизм
восстановления публикации. Иначе возможна ситуация, когда метаданные
записаны, а событие не опубликовано.

## 7.2. Алгоритм распознавания и группировки лиц

**Подсистема:** фоновая обработка фотографий, профили лиц и индекс
поиска по лицам.

**Задача:** определить, соответствует ли лицо на новой фотографии одному
из ранее созданных профилей пользователя, и обеспечить поиск фотографий
по найденному человеку.

**Входные данные и ограничения:** - идентификатор владельца
фотографии; - изображение или область изображения с обнаруженным
лицом; - модель, формирующая векторное представление лица; - профили лиц
пользователя и порог сходства; - эмбеддинг лица размерностью 512
значений типа `FLOAT32` (около 2048 байт без учёта накладных расходов).

**Результат:** эмбеддинг сохранён; лицо связано с существующим профилем
либо для него создан новый профиль/неразобранная группа; обратный индекс
фотографий обновлён.

**Последовательность работы:**

1.  Обработчик получает событие о загруженной фотографии и загружает
    изображение из Ceph.

2.  Модель компьютерного зрения обнаруживает лица на изображении.

3.  Для каждого лица модель вычисляет эмбеддинг --- вектор признаков
    размерностью 512.

4.  Система получает профили лиц соответствующего пользователя из
    `face_profiles`.

5.  Для каждого профиля вычисляется косинусное расстояние между
    эмбеддингом нового лица (x) и центроидом профиля (c):

    ```math
    d(x,c)=1-\frac{x\cdot c}{\|x\|\|c\|}
    ```

6.  Если минимальное расстояние не превышает заданный порог
    ($\tau$), лицо связывается с соответствующим профилем. Если ни
    один профиль не подходит, система создаёт новый профиль либо
    помещает лицо в неразобранную группу.

7.  Эмбеддинг сохраняется в `face_embeddings`, связь фотографии с
    профилем --- в `face_photos`, а необходимые поисковые атрибуты
    обновляются в `search_index`.

8.  При повторной обработке события система должна избегать создания
    дубликатов и повторного добавления одной и той же связи.

**Используемые структуры данных:** `face_profiles` хранит профили и
центроиды; `face_embeddings` --- векторные представления обнаруженных
лиц; `face_photos` --- обратный индекс фотографий по владельцу, профилю
лица и году; `search_index` --- поисковые атрибуты фотографии.

**Альтернативы и обоснование выбора:**

- **Сравнение со всеми ранее найденными эмбеддингами.** Может точнее
  учитывать разнообразие внешности одного человека, но увеличивает
  объём сравнений и стоимость обработки.
- **Сравнение с центроидами профилей.** Сокращает количество сравнений
  и упрощает реализацию, поэтому подходит как базовый вариант MVP.
- **Индекс приближённого поиска ближайших соседей (ANN).** Может быть
  полезен при очень больших коллекциях профилей, но требует
  дополнительной инфраструктуры и отдельного обслуживания индекса.

**Влияние на БД и нагрузку:** распознавание выполняется асинхронно на
отдельных worker-процессах, которые можно масштабировать независимо от
API. Число сравнений зависит от количества профилей конкретного
пользователя. Порог ($\tau$) необходимо подбирать экспериментально
на репрезентативном наборе данных: слишком высокий порог увеличит число
ошибочных объединений, а слишком низкий --- число разделённых профилей
одного человека. Описанный алгоритм отвечает за сопоставление эмбеддинга
с профилями; обнаружение лиц и вычисление эмбеддингов выполняются
отдельной ML-моделью.

## 7.3. Алгоритм поиска фотографий по метаданным и лицам

**Подсистема:** Search Service, поисковый индекс Cassandra и индекс
фотографий по лицам.

**Задача:** находить фотографии пользователя по дате, камере,
географическому положению и человеку без полного сканирования всей
коллекции.

**Входные данные и ограничения:** - идентификатор владельца; - диапазон
дат или год; - необязательные фильтры: модель камеры, географическая
ячейка, идентификатор профиля лица и другие поддерживаемые атрибуты; -
курсор пагинации и лимит результатов.

**Результат:** упорядоченный список идентификаторов фотографий и
доступных метаданных, соответствующих фильтрам.

**Последовательность работы:**

1.  Сервис проверяет авторизацию и определяет владельца, от имени
    которого выполняется поиск.
2.  Запрос нормализуется: даты приводятся к единому формату, проверяется
    корректность диапазонов и допустимость фильтров.
3.  Для обычного поиска сервис ограничивает выборку партицией владельца
    и годом в `search_index`, ключ которой имеет вид
    `((owner_id, year), created_at DESC, photo_id)`.
4.  Фильтры по камере, географической ячейке и другим атрибутам
    применяются с использованием предусмотренных индексов Cassandra SAI,
    если сочетание фильтров поддерживается выбранной версией Cassandra.
5.  Для поиска по человеку сервис обращается к `face_photos`, где ключ
    партиционирования включает владельца, идентификатор лица и год.
6.  Результаты возвращаются страницами с использованием курсора или
    keyset-пагинации, чтобы не загружать всю коллекцию за один запрос.
7.  При необходимости сервис объединяет результаты нескольких годовых
    партиций и удаляет дубликаты по `photo_id`.

**Используемые структуры данных:** `search_index` для поиска по
метаданным; `face_photos` для поиска по профилю лица; составные ключи
Cassandra для ограничения области чтения; курсор пагинации для
последовательного получения результатов.

**Альтернативы и обоснование выбора:**

- **Полное сканирование таблицы.** Просто в реализации, но неприемлемо
  для коллекции из триллионов фотографий: стоимость чтения и задержка
  будут слишком высокими.
- **Отдельный поисковый движок, например Elasticsearch/OpenSearch.**
  Предоставляет развитые возможности полнотекстового поиска и
  комбинирования фильтров, но требует отдельного кластера,
  синхронизации данных и дополнительной эксплуатации.
- **Cassandra с денормализованными таблицами и SAI.** Позволяет
  хранить поисковые проекции рядом с остальными данными и
  масштабировать чтение горизонтально. При этом запросы должны
  соответствовать модели ключей, а поддерживаемые сочетания
  SAI-фильтров необходимо проверить для выбранной версии Cassandra.

**Влияние на БД и нагрузку:** запросы ограничиваются данными конкретного
владельца и небольшими временными диапазонами, что сокращает объём
чтения. Денормализация ускоряет поиск, но увеличивает объём хранения и
количество записей при загрузке фотографии. Индексы не отменяют
необходимости контролировать размер партиций, ограничивать число
возвращаемых строк и проверять реальные планы выполнения запросов.

## 7.4. Алгоритм формирования уведомлений при изменении общего альбома

**Подсистема:** управление общими альбомами, распространение событий и
доставка уведомлений.

**Задача:** уведомлять участников общего альбома об изменениях, не
блокируя пользовательский запрос ожиданием доставки уведомлений и не
теряя события при временных сбоях.

**Входные данные и ограничения:** - идентификатор события и тип
изменения; - идентификатор альбома и инициатора изменения; - список
участников и их права доступа; - настройки уведомлений получателей; -
ограничения на частоту отправки и повторные попытки.

**Результат:** событие об изменении альбома обработано, записи
уведомлений сохранены, а задания на доставку переданы в очередь.
Фактическая доставка может происходить с задержкой.

**Последовательность работы:**

1.  Сервис в одной транзакции PostgreSQL изменяет данные альбома или его
    состав и записывает событие в таблицу transactional outbox.
2.  Debezium отслеживает изменения outbox и передаёт событие в Kafka.
3.  Обработчик определяет участников альбома, которым положено
    уведомление, исключая инициатора, если он не должен получать
    уведомление о собственном действии.
4.  Для каждого получателя создаётся запись уведомления в Cassandra.
    Событие получает стабильный идентификатор, позволяющий обнаруживать
    повторную обработку.
5.  Задания на доставку помещаются в RabbitMQ. Отдельные workers
    отправляют push-уведомления или передают их соответствующему сервису
    доставки.
6.  При временной ошибке сообщение повторно ставится в обработку с
    задержкой. После исчерпания числа попыток оно направляется в очередь
    ошибок для последующего анализа.
7.  Обработчики подтверждают сообщение только после выполнения
    необходимой операции сохранения или передачи. Повторная доставка не
    должна приводить к созданию дубликатов уведомлений.

**Используемые структуры данных:** таблицы альбомов и участников в
PostgreSQL, transactional outbox, события Kafka, таблица `notifications`
в Cassandra, очередь RabbitMQ и очередь ошибок.

**Альтернативы и обоснование выбора:**

- **Синхронная отправка из API.** Проще, но повышает задержку ответа и
  делает API зависимым от доступности внешних каналов доставки.
- **Публикация в Kafka без transactional outbox.** Может потерять
  событие между фиксацией изменения в PostgreSQL и публикацией в
  брокер.
- **Использование одного брокера для всех этапов.** Может упростить
  архитектуру, однако Kafka удобна для событийного потока и повторного
  чтения, а RabbitMQ --- для очереди заданий доставки с
  подтверждениями и повторными попытками.

**Влияние на БД и нагрузку:** пользовательский запрос выполняет только
изменение данных и запись события в outbox. Формирование и доставка
уведомлений масштабируются независимо. Модель доставки является как
минимум однократной (at-least-once), поэтому возможны повторные
сообщения; стабильные идентификаторы событий, идемпотентная обработка и
дедупликация необходимы для предотвращения дубликатов. Денормализованные
данные доступа, если они обновляются асинхронно, могут временно
отставать от исходных таблиц; окончательная проверка прав доступа должна
опираться на источник истины.
